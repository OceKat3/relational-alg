Project 2

Build a database system, one module at a time

Structure Four modules plus integration Time Six weeks Work Individual Submit GitHub, five checkpoints

You are building a working database system. Not a simulation of one. Text goes in as SQL, a plan comes out, and tuples are read from pages on disk through a buffer pool you wrote.

The system is split into four modules. Each one is defined by a contract, runs on its own through its own command line tool, and is graded on its own at its own checkpoint. You do not need the later modules to finish an earlier one, and a module that works alone but does not meet its contract will not compose with the others later. The last two weeks join them into one system.

This is long. Nothing here is conceptually out of reach for a third year student, but there is a great deal of it, and the modules build on each other in a way that punishes shortcuts taken early. Bonus Project 1 is a prerequisite, for the reason given in Section 1.2.

1  How the project is organised

1.1  The four modules

Module What it does Contract boundary
M1 Storage engine. Pages on disk, heap files, a buffer pool, a catalog. Page and tuple access API
M2 Execution engine. Iterator operators, external sort, three join algorithms, all under a memory budget. Physical plan JSON in
M3 SQL front end. Hand-written parser, name resolution, type checking, translation to relational algebra. SQL in, logical plan JSON out
M4 Optimizer. Statistics, selectivity estimation, rewrites, cost-based choice of join order and algorithm. Logical plan in, physical plan out

The contracts are what make the modules independent. M2 consumes a physical plan written as JSON, so it can be tested long before an optimizer exists. M4 produces that same JSON, so it can be tested without a working executor. I will evaluate each module by feeding it files of my own and reading what comes out.

This handout is the overview. Each module has its own specification document on Brightspace, and those are the documents you build from. They give exact byte layouts, exact JSON field names, cost formulas, and worked examples with numbers your implementation must reproduce.

M1 Storage Engine and Buffer Pool. Page and record formats to the byte, heap file operations, both replacement policies with a trace you must reproduce exactly.
M2 Execution Engine. Every operator with its semantics, its memory allowance, its cost formula and its counter rules. Worked examples for the external sort and for duplicate join keys.
M3 SQL Front End. The grammar, name resolution rules, bag semantics, and seven translation examples showing the plan each SQL construct must produce.
M4 Query Optimizer. Statistics, selectivity formulas, seven rewrite rules with their preconditions, the cost model, and a dynamic programming table worked through by hand.

Where this handout and a module document disagree, the module document is correct. Read the one for your current checkpoint before you write any code for it.

1.2  Who can take this on

You must have completed Bonus Project 1 and submitted it. There is no reference implementation and no alternative entry point. This is not a formality. Your relational algebra engine is the logical layer of the system you are about to build, and three of the four modules reach into it. Work is individual, as it was for Bonus Project 1. You may discuss approaches with other students and you may use AI, but the code and the documents are yours alone.

If you did not do Bonus Project 1, this project is closed to you. Spend the time on the regular final project instead.

1.3  Week one, prepare your engine

Before Module 1 starts, spend the first week turning your Bonus Project 1 code into something the rest of the system can use. It was written as a standalone program. It now has to be a library that three other modules call. This is unglamorous work and it is the cheapest week of the project to get right.

1 Separate the layers. The tokenizer, the parser, the tree and the operators must be four things that can be imported independently. Nothing in them may print to the screen or read a file directly. A library that writes to standard output is unusable inside a query engine.
2 Expose the condition parser on its own. Modules 2, 3 and 4 all need to parse a condition string such as R.b = S.b into a tree and evaluate it against a tuple. That is the single most reused piece of code you already own.
3 Support qualified names everywhere. Every column reference in this project is table.column. If your Bonus 1 engine only half handled qualification, fix it now rather than in Module 3.
4 Serialise the tree. Your plan tree must be writable as JSON and readable back, because JSON is the contract between every pair of modules. Write the two functions and a test that round-trips every node type.
5 Detach the operators from their data source. In Bonus 1 your operators read relations held in memory. They must now pull tuples from something you pass in. You do not need the iterator interface yet, Module 2 defines it, but the dependency on in-memory lists has to go.
6 Move from sets to bags. Bonus 1 removed duplicates inside projection, because relational algebra is defined on sets. SQL is not. Projection must now keep duplicates and duplicate removal becomes a separate operator. Module 3 explains why in detail.
7 Keep the test suite. All twenty five Bonus 1 cases must still pass after the refactor, except the ones that changed meaning under point 6. Say in your log which ones changed and why.

This work is graded as part of the Module 1 checkpoint.

1.4  Conventions that hold across all four modules

Page size 4096 bytes, fixed. Everything is measured in pages.
Types INT (4 bytes, signed) and VARCHAR(n) with n up to 255. No NULL values anywhere in this project.
Memory budget Every tool takes --frames B. Your system may hold at most B pages in memory at any moment. Exceeding it is a correctness failure, not a performance one.
Counters Every tool takes --json and emits page reads, page writes, and per-operator tuple counts. These numbers are how each module is graded.
Libraries No database engines, no pandas, no parser generators, no regular expressions in any lexer or parser. A JSON library is allowed. A plotting library is allowed in reports. Your language's standard sort is allowed for sorting a single in-memory run, but not for the external sort as a whole.
Determinism Given the same data, the same plan and the same B, your counters must be identical across runs. If they are not, something in your system is not under your control.

2  Module 1. Storage engine and buffer pool

Everything above this module eventually asks it for a page. It is the only code in the system permitted to touch a file.

2.1  What you build

A disk manager that reads and writes fixed 4 KB pages by page id and counts every read and write. A slotted page layout that stores variable length records, with a slot directory growing from the front and record data from the back. A heap file built from those pages, with a free space directory so that an insert does not scan every page. A buffer pool with a fixed number of frames, pinning, dirty tracking and a replacement policy. A catalog, itself stored in pages, holding table names, schemas and the first page of each heap file. A bulk loader that reads a CSV file into a table.

Two replacement policies, LRU and CLOCK, selectable at startup. You will be asked to explain where each one fails.

2.2  The contract

Names may differ in your language. Behaviour may not.

DiskManager
  read_page(page_id) -> 4096 bytes          // counts one read
  write_page(page_id, bytes)                // counts one write
  allocate_page() -> page_id
  num_pages() -> int

BufferPool(frames B, policy)
  fetch_page(page_id) -> page               // pins it
  unpin_page(page_id, is_dirty)
  new_page() -> page                        // pinned
  flush_all()
  stats() -> { hits, misses, evictions, reads, writes }
  // evicting a pinned page is an error, not a silent choice

HeapFile(table)
  insert(tuple) -> rid                      // rid = (page_id, slot)
  get(rid) -> tuple
  delete(rid)
  scan() -> iterator of (rid, tuple)        // one page pinned at a time

Catalog
  create_table(name, schema)
  get_table(name) -> { schema, first_page, num_pages, num_tuples }
  list_tables()

The scan constraint matters. A scan holds one page pinned at a time, not the whole file. A scan that materialises the table into a list defeats the entire module and will be visible in your counters.

2.3  How it runs standalone

storage create-table --name R --schema "a:INT,b:VARCHAR(20),c:INT"
storage load        --table R --file r.csv
storage scan        --table R --limit 20 --frames 8 --json
storage layout      --table R --page 3          // dumps slots and offsets
storage trace       --file trace.txt --frames 16 --policy lru --json

The trace command is how I grade your buffer pool. A trace file holds one page id per line. Your pool processes them in order and prints hits, misses, evictions and writes as JSON. I supply the traces. Three of them are published with this handout, and two are not.

The layout command prints the raw structure of one page, slot by slot, with byte offsets. It must agree with the diagram in your design document.

2.4  Required measurements

Compute by hand how many records of a given schema fit on one 4 KB page under your layout, then load data and measure it. Explain any gap between the two numbers. Repeat for a schema with a long VARCHAR and for one with only INT columns.

Run all five traces under both policies at four pool sizes and report hit rates in one table. One of the published traces is a repeated sequential scan of a file larger than the pool. Report what LRU does there, explain why, and say which policy you would ship.

2.5  Deliverables

Working code behind the five commands above. DESIGN_M1.md with a byte-level diagram of your page header, slot directory and record format, plus your free space strategy and your reasoning. REPORT_M1.md with the two measurement tables. Tests, including a test that evicting a pinned page fails.

3  Module 2. Execution engine

This module takes a physical plan and runs it against the storage engine, inside a memory budget it is not allowed to exceed. It is the largest of the four.

3.1  What you build

Every operator implements the same three method interface, and a plan is a tree of them. Calling next on the root pulls one tuple through the whole tree. Nothing materialises a full intermediate result unless the operator genuinely requires it, which is true only for sort and for the build side of a hash join.

Operator Requirement
seqscan Streams a heap file one page at a time through the buffer pool.
filter, project Fully pipelined. Constant memory.
sort External merge sort. Sorts input larger than B pages by writing runs to disk and merging them. Must work when the input is twenty times B.
distinct, group_by Both a sort-based and a hash-based implementation. Aggregates COUNT, SUM, AVG, MIN, MAX.
nested_loop_join Block nested loop. Reads the outer in blocks of B minus 2 pages.
sort_merge_join Built on your external sort. Must handle duplicate join keys on both sides correctly.
hash_join Grace hash join. Partitions both inputs to disk, then joins partition by partition. Must detect a partition that still exceeds B and do something defensible.
union, intersect, except Bag and set versions of each.

3.2  The contract

Operator
  open()
  next() -> tuple, or end-of-stream
  close()
  counters() -> { tuples_out, comparisons, page_reads, page_writes }

A physical plan arrives as JSON. This is the format, and it is the same format Module 4 produces.

{
  "op": "hash_join",
  "condition": "R.b = S.b",
  "left":  { "op": "filter",
             "condition": "R.a > 500",
             "child": { "op": "seqscan", "table": "R" } },
  "right": { "op": "seqscan", "table": "S" }
}

Condition strings are parsed by the expression parser you already wrote in Bonus Project 1. The full JSON schema for every operator is published alongside this handout. Your executor must reject a plan that does not conform, with a message naming the offending node.

Plan validation and error reporting. A plan whose JSON is malformed or does not conform to the expected plan schema must be rejected before execution. Error messages must provide enough information to identify and fix the problem.

For schema-validation errors, the message must identify the offending node (e.g., sort, filter, or hash_join) and describe the specific problem, such as a missing required field, an invalid field value, an unsupported operator, or an incorrectly structured field. For example:

  • Node 'sort': missing required field 'keys'.

  • Node 'filter': field 'condition' must be a string.

  • Node 'join': unknown operator 'merge_join'.

For malformed JSON syntax, report the syntax error and its location when possible. The exact wording and output format are implementation-defined; the messages must be sufficiently specific to diagnose the error.

A plan referring to an unknown table or column must be rejected at open, before any execution work begins.

3.3  How it runs standalone

exec run   --plan plan.json --frames 32 --json
exec trace --plan plan.json --frames 32        // per-operator counters

I will supply plan files and a dataset. Your output is checked for correct tuples, as a bag, and your counters are checked against what the algorithm named in the plan should cost.

3.4  Required measurements

For each of the three joins, measure page reads and writes across at least four values of B and three relation sizes, and put the measured numbers beside the textbook cost formula in one table. Block nested loop should cost M + ⌈M/(B−2)⌉·N page reads. Where your measurement differs, explain the difference. The explanation is worth more than the agreement.

Find the crossover point. For a fixed pair of relations, vary B and report which join algorithm is cheapest at each value. Then do the same varying relation size at fixed B. Plot both.

Measure the number of passes your external sort makes against ⌈logB−1(N/B)⌉ + 1 and report both.

Build a dataset where one join key value appears in a large fraction of the rows, run the hash join on it, and report what happened to your partitions and what your code did about it.

3.5  Deliverables

Code behind both commands. DESIGN_M2.md describing how each operator respects the memory budget, with the page accounting for sort and hash join written out. REPORT_M2.md with the four measurements above. Tests including duplicate join keys, empty inputs and a join whose output is larger than either input.

4  Module 3. SQL front end

Bonus Project 1 turned relational algebra text into a tree. This module turns SQL into the same kind of tree, which is harder, because SQL does not say what order to do anything in.

4.1  The SQL subset

CREATE TABLE name (col TYPE, ...)
INSERT INTO name VALUES (...)
SELECT [DISTINCT] select_list
  FROM table_ref [, table_ref ...] | table_ref JOIN table_ref ON condition
 [WHERE condition]
 [GROUP BY cols [HAVING condition]]
 [ORDER BY cols [ASC|DESC]]
 [LIMIT n]
query UNION [ALL] query | INTERSECT | EXCEPT

Table references may carry an alias. A table reference may also be a parenthesised subquery with an alias. Aggregates are COUNT, SUM, AVG, MIN and MAX, including COUNT(*).

4.2  What you build

A hand-written lexer and parser, under the same rules as Bonus Project 1. No regular expressions, no parser generators. A grammar document again, since SQL's grammar is considerably larger and the precedence questions are real.

Then a semantic analysis pass against the catalog, which resolves every column reference to exactly one table, expands SELECT *, type checks every comparison, and rejects an aggregate used outside an aggregating query. Then a translator that emits a logical plan.

The hard part is semantics, not syntax. SQL works on bags and your Bonus 1 algebra worked on sets. You must decide where duplicate elimination actually belongs, make UNION remove duplicates while UNION ALL does not, and be able to explain why SELECT DISTINCT is not free. This is the single most common place where a plausible looking implementation is silently wrong.

4.3  The contract

Output is a logical plan in JSON. Logical operators are scan, select, project, join, rename, group_by, distinct, sort, limit, union, intersect, except. No physical choices appear here. A logical plan says join, never hash join.

sql parse   --query "SELECT ..." --explain        // prints the tree
sql compile --file q.sql --catalog db/ --json     // logical plan JSON
sql check   --file q.sql --catalog db/            // errors only

4.4  Cases that must work

1 A self join written with two aliases on the same table, translating into a rename.
2 SELECT * over a three table join where two tables share a column name.
3 An unqualified column that exists in two tables. Must be rejected as ambiguous.
4 UNION against UNION ALL on the same inputs, producing different plans.
5 A WHERE condition and a HAVING condition in one query, landing on opposite sides of the grouping.
6 A non-aggregated column in the select list of a GROUP BY query. Must be rejected.
7 A subquery in the FROM clause with an alias, joined to a base table.
8 ORDER BY on a column that is not in the select list.
9 Comparing an INT column to a string literal. Type error, as in Bonus Project 1.
10 A query against a table that does not exist, and one against a column that does not exist. Different messages.

4.5  Deliverables

Code behind the three commands. GRAMMAR_SQL.md, the EBNF for your subset with precedence and associativity, in the style of Bonus Project 1. DESIGN_M3.md covering name resolution and your bag semantics decisions, with the place where duplicate elimination happens justified. Tests for all ten cases.

5  Module 4. Query optimizer

A logical plan says what. A physical plan says how. This module chooses, and the choice is worth orders of magnitude.

5.1  What you build

Statistics gathering, triggered by an ANALYZE command and stored in the catalog. Per table, row count and page count. Per column, number of distinct values, minimum, maximum, and an equi-depth histogram with a configurable bucket count.

Selectivity estimation for equality, range, conjunction and disjunction, and for a join. State your formulas and your assumptions in the design document, because you will be asked to show where they break.

Rule-based rewrites on the logical plan. Splitting conjunctions, pushing selections toward the leaves, pushing projections down, and removing a projection that discards nothing.

Then the cost-based part. A cost model counting page I/O as a function of B. Enumeration of join orders by dynamic programming over left-deep trees, for queries with up to six relations. For each join, a choice among your three algorithms. The output is a physical plan in the exact JSON that Module 2 consumes.

5.2  The contract

opt analyze  --catalog db/ --table R --buckets 20
opt plan     --logical logical.json --catalog db/ --frames 32 --json
opt explain  --logical logical.json --catalog db/ --frames 32
opt dp-table --logical logical.json --catalog db/   // the DP table, one row per subset

Every node in an explain output carries its estimated row count and its estimated cost. This is what I read when grading, and it is what you read when your optimizer makes a decision you do not understand.

5.3  Required measurements

For the twenty supplied queries, report estimated against actual row count at every node, as a q-error, which is the larger of the two divided by the smaller. Give the median and the worst case. A median near 1 means your estimates are good. A worst case in the hundreds is normal and is the interesting part of the report.

For each query, measure the I/O of your chosen plan against the plan you would get with no optimizer at all, meaning joins in the order written and one fixed algorithm. Report the ratio.

The supplied dataset contains two columns that are strongly correlated. Find a query where this makes your optimizer choose a bad plan. Show the estimate, show the actual, name the assumption that failed, and measure how much that plan cost you against the better one. This question is worth more than the rest of the module's report combined.

5.4  Deliverables

Code behind the four commands. DESIGN_M4.md with your cost model, your selectivity formulas, your rewrite rules and your enumeration strategy, including why left-deep and what you lose by that restriction. REPORT_M4.md with the three measurements. The DP table for one four table join, printed in full.

6  Integration

In the last two weeks the four modules become one program. A single binary with a prompt, where SQL goes in and rows come out.

  SQL text
     |
     v
  [ M3 ]  lexer -> parser -> semantic analysis -> translation
     |
     |  logical plan
     v
  [ M4 ]  rewrites -> statistics -> cost model -> join order -> algorithm choice
     |
     |  physical plan
     v
  [ M2 ]  iterator tree, open / next / close, memory budget B
     |
     |  page requests
     v
  [ M1 ]  buffer pool -> heap files -> pages on disk
                   ^
                   |
              catalog and statistics, read by M4

The shell supports the SQL subset plus EXPLAIN, EXPLAIN ANALYZE, ANALYZE table, SET frames = n, and LOAD table FROM file. The four module command line tools must still work. Integration means wiring, not rewriting.

Seventy two hours before the demo I publish a dataset and twenty five queries you have not seen. You load the data, run the queries, and report for each one the result row count, the page I/O, the wall time, and the estimated against actual rows at the root. Correctness is checked by running the same queries on PostgreSQL over the same data on your OpenStack instance. Your system does not need to be fast. It needs to be right, and your numbers need to explain themselves.

ARCHITECTURE.md describes the whole system, the interface between each pair of modules, and one page on what you would do differently if you started again.

9  Using AI on this project

Allowed, and you will use it. It will also mislead you more here than it did on Bonus Project 1, because the hard parts of this project are not code. They are the memory budget your sort has to respect, the statistics your optimizer trusts too much, and the fact that your four modules were written at four different times by people who had changed their minds in between.

Each checkpoint carries a DESIGN_LOG.md entry. What you tried, what broke, and at least two places per module where AI assistance gave you something wrong, slow or quietly incorrect, with how you found it. A log saying you asked and it worked scores zero.

You are examined on every module, including the ones you finished weeks earlier. Code you cannot explain scores zero for that checkpoint whether or not it runs.
