So like, high level, text from the repl -> sql parse tree -> sql AST -> relational algebra AST -> physical plan AST. and then some nodes inside the physical plan call out to the storage engine, and the root node of the physical plan outputs an in-memory relation to print to the rep, and/or it writes stuff to disk.

Hmm okay aggregation is getting complicated again. The SQLContext.in_aggregate_function is not sufficient maybe, i just need to think it through

in a regular SQL query you can use any attribute anywhere, because it's not in GROUP BY and it's also not in an aggregate function. 
in an aggregate SQL query (without group by) you can only use aggregate functions in the output, it's the same as having group by nothing. So attributes don't work because the query is aggregate but they are not aggregated and not in an aggregate function
in an aggregate SQL query with groupby, then you can use the grouped attributes outside of an aggregate function, and the non-grouped attributes inside an aggregate function. You also can't use grouped attributes inside an aggregate function
